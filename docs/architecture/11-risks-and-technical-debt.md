# 11. Risks & Technical Debt

Known risks and areas that warrant care. Documented so they are visible, not
hidden.

## 11.1 Operational risks

| Risk | Impact | Mitigation / status |
|---|---|---|
| **NetBird sidecar is a SPOF** when it shares the gateway's network namespace | A sidecar crash can 502 the whole public API (including login) | Prefer the no-netbird deployment where the mesh is not needed; monitor the sidecar; the wrapper enrolls via a key file to reduce misconfiguration. |
| **PostgreSQL narrow-type truncation** surfaces only on real PostgreSQL | Silent data truncation/precision loss if a column type is too narrow | Wide types are mandated (`bigint`/`double precision`); run the conformance suite against PostgreSQL before shipping store changes (see [ADR-005](09-architecture-decisions.md#adr-005--postgresql-needs-wide-column-types)). |
| **Payload capture holds plaintext in RAM** in the volatile mode | OS swap or a core dump could place prompt/response plaintext on disk | Documented as out of scope; the guarantee is "never written to disk by the application" (see [ADR-008](09-architecture-decisions.md#adr-008--payload-capture-opt-in-encrypted-or-volatile-redacted)). |
| **Privileged telemetry sources absent** when the agent runs unprivileged | Some power/temperature/per-DIMM data is unavailable | By design; the agent degrades gracefully and reports what it can. |
| **Public ACME / SMTP / OTLP unavailable** in air-gapped setups | Edge certs, e-mail invites, and trace export are unavailable | All are opt-in; the system runs without them. |
| **A proxy-switched application whose agent reports `tls_active:false` stays `https` and is unreachable** | An expired leaf, a taken proxy port or a failed bind takes that application out of service until TLS is restored — the gateway no longer degrades it to plaintext | Deliberate operator decision: never answer an environment failure by turning encryption off ([ADR-017](09-architecture-decisions.md#adr-017--agent-tls-proxy--https-auto-switch-scope-exit-revert-but-no-downgrade-on-broken-tls)). Made non-silent in two independent places — a `Warn` on **every** reconcile pass naming server, application, port, the agent's own `RouteState` reason and the remedy, and `Service.HTTPSSwitchUnreachableApps`, returned by `GET /api/system/certificates` under `https_switch.unreachable_apps` and rendered as an **error** alert by the portal's certificate view. Self-healing: the application was never moved, so it works again the moment the listener returns — there is no forward switch to re-run and no window in which it is briefly plaintext. The **scope-exit** revert to `http` is the one automatic move to plaintext that deliberately survives this ([certificates-tls §7.1](cross-cutting/certificates-tls.md#71-no-automatic-downgrade-to-plaintext)). |
| **The agent is a SPOF for its server's managed models** ([agent-managed model runtime](cross-cutting/agent-runtime-manager.md)) | If the agent dies, every model it manages becomes unreachable — the router is the only way in | Accepted by construction; the mitigation is the migration path, since classic non-managed applications may coexist on the same server, so llama-swap and the managed runtime can run side by side. |
| **A portal admin with server-management rights effectively chooses what runs on the AI servers** | Portal write access selects binary, argv, env and working directory for a process on the AI server | Bounded **only** by the agent-local binary allowlist, which is operator-controlled on each host and starts nothing when empty ([ADR-024](09-architecture-decisions.md#adr-024--managed-runtime-the-gateway-specifies-the-launch-the-ai-server-permits-it)). Enabling the feature is an explicit act per host and the gateway cannot widen it. |
| **The agent's model-runtime router authenticates nothing, and its shipped default binds all interfaces** | Every managed model on that host is reachable from any interface that can reach the port | `runtime_router_bind` / `OP_AGENT_RUNTIME_ROUTER_BIND` is the operator's control (mesh IP, or `127.0.0.1`). The empty-value fallback derives a mesh address from the installed leaf certificate, but `DeriveBindHost` takes `cert_dir` as its single argument and **never consults `cert_mode`** — so what it needs is a loadable leaf with a usable SAN in that directory, and a populated `cert_dir` left behind after the mode was switched to `"off"` still derives one. The portal's generated agent config ships `cert_mode: "off"` with an **empty `cert_dir`**, and that empty directory — not the mode — is why **the shipped default always falls through to all interfaces**, logged at Warn. Set it explicitly. |
| **A *literal* secret placed in a launch spec's `args` reaches the gateway unmasked** | The upward file-mode report masks `env` values, a literal `api_token` and config-file content, and sends `args` verbatim | Reviewed and upheld as spec-correct: the report's wire contract scopes redaction to `env` values, the `api_token` and config-file content, and leaves `args` outside it. **Narrowed, not closed:** the resolved launch command the log stream reports masks every `${AGENT_ENV:NAME}`-derived value in `args` as well as in `env`, by recorded provenance ([agent-runtime-manager §14.7](cross-cutting/agent-runtime-manager.md#147-the-resolved-command-what-actually-ran)), so the new channel does not inherit the asymmetry. What remains open is a *literal* value typed into a spec — which the gateway already holds in plaintext anyway — and the child's own output, which no masking can reach. **Operator guidance: reference secrets as `${AGENT_ENV:NAME}`, and keep them in `env`.** |
| **`work_dir` containment for managed processes is lexical** — symlinks under an allowed directory can point outside it | A spec could run an allowlisted binary with its working directory effectively outside the permitted tree | Accepted. The security boundary is `runtime_allowed_binaries` (an exact absolute-path match against the agent's own local list), so a gateway-supplied spec cannot choose *what* executes; `work_dir` only decides where an already-allowlisted binary resolves relative paths, and an attacker able to plant symlinks there already has local write access. `filepath.EvalSymlinks` was **rejected deliberately, not overlooked**: it resolves at *check* time while `os/exec` applies the directory at *start* time, so anything able to rewrite the link between those moments defeats the check **while making it look enforced** — strictly worse than an honest lexical check, because it invites treating containment as a boundary. It would also break the legitimate case of an allowed directory that is itself a symlink to a mounted volume. If containment ever has to *be* a boundary, the non-TOCTOU direction is `openat`/`O_NOFOLLOW` resolution plus `fchdir` in the child, which `exec.Cmd.Dir` cannot express portably. |
| **Windows managed-process stop is kill-only** | On a Windows AI server a stop terminates the child rather than letting it finish in-flight work — there is no graceful-drain equivalent | Accepted for now; the code compiles and looks complete, so the gap is only discoverable by reading the platform file. A real fix needs `CREATE_NEW_PROCESS_GROUP` plus `GenerateConsoleCtrlEvent`. **Correction: CI does not check this — it compiles nothing for Windows at all** (see §11.3), so `proc_windows.go` is never built there; cross-compile locally with `GOOS=windows GOARCH=amd64 go vet ./...` before changing it. |
| **Volatile runtime status loses `last_error` on an agent restart** | The last load failure for a managed model is gone after the agent restarts | Honest and documented, not a defect: gateway-side status is deliberately never persisted (a stderr tail can carry prompt fragments, which the capture policy forbids at rest), and a gateway restart self-heals within one ~1 s sample. Only an *agent* restart loses it permanently. |
| **The runtime report is fetched once per (api, server), with no polling refresh** | A file-mode agent's re-report after a config-file edit is only picked up on a remount or navigation | Deliberate split: the report is navigation-fresh, live status rides the SSE stream. Switching to a polled fetch is a small change if operators need it. |
| **A pairwise co-residency matrix plus per-GPU arithmetic cannot express every constraint** | Exotic interconnect or bandwidth contention is not modelled | Accepted: the matrix's role is operator *intent*, which covers the known non-VRAM cases (PCIe bandwidth, system RAM, CPU contention) that nobody can compute. |
| **File mode offers no remote operations, and gateway-side specs become invisible while it is active** | An operator cannot view or delete the now-ineffective gateway-side runtime specs from the portal | By design — whoever owns the configuration owns the operations, and the file-mode view is display-only. Operator guidance: switch the agent's source back to `gateway` to inspect or remove that dormant configuration. |
| **There is no one-shot "retry this model" action** | For a `stopped` row carrying a `last_error` — the headline failure case — the only affordance is `force_running`, a **persistent** override that must be cleared afterwards | A limitation of the state-shaped runtime API ([ADR-026](09-architecture-decisions.md#adr-026--gatewayagent-control-is-desired-state-not-commands)), not of the screen; restart is unavailable there because a `force_stopped` write with no live process does nothing at all. |
| **Two `server_agent` applications on one server make both un-editable from the portal** | Saving *any* field change sends `type: "server_agent"`, the uniqueness gate finds the other row, and the request is refused with a 409 naming a condition the operator did not try to create | Only reachable on a pre-invariant development database (the type is unwritable in every released version). The remediation is deleting one application, not editing around it. Related: the service-layer gate has a real TOCTOU — it reads, releases the lock, then writes with no transaction, so two concurrent creates can both pass it (reproduced 2 times in 200) — and the backstops that catch the race loser are migration 68's index on SQL and an explicit locked check in the memory store. **The service gate is not race-free and must not be described as such**, nor either backstop removed as "redundant with it". **Corrected on this branch:** the race loser no longer surfaces as the misleading `application.port_conflict`. `classifyApplicationWriteConflict` re-reads the server's applications on the already-failed write and returns `ErrServerAgentApplicationExists` → 409 `application.server_agent_exists` when another `server_agent` row is what it finds, so no dialect-specific error text has to be parsed (the re-read pattern is documented in [Persistence](cross-cutting/persistence.md)). The port check runs first, deliberately, so a genuine port collision still reports as one. **Also corrected on this branch:** the portal now says so *before* the save. Both duplicates' edit forms disable the `server_agent` option and name the rule and its remedy under the type field, while the field still renders `server_agent` as its value (a closed MUI select computes its text from the matching item regardless of that item's disabled state) — so nothing is blanked, the 409 is still what refuses the write, and the remediation is unchanged. |
| **`runtime_max_processes` on the runtime screen is never re-seeded from props** | A value another admin changed meanwhile is overwritten on Save | Left as-is deliberately: this is the ordinary controlled-form-draft-versus-prop tension the whole portal shares, not an instance of the load-gate class the same screen hardened against. |
| **The models list does not surface agent-managed runtime state** | "Currently loading" and "last load failed" are visible only on the runtime admin screen | Named rather than fixed: surfacing them would need new plumbing (either the model DTO or a new props path carrying per-mapping runtime state), so the gap is not a five-minute change. |
| **The `managed_runtime_only` checkbox can display a value another operator has since changed** | The server form seeds the checkbox when it opens and never re-seeds it, so a flag flipped elsewhere mid-edit is shown stale — the same controlled-form-draft-versus-prop tension as the `runtime_max_processes` row above. | Accepted, and deliberately kept *display-only*. The write path does not inherit the staleness: `submitEdit` sends `managed_runtime_only` only when the checkbox differs from the value it was seeded with, so a save made for an unrelated reason omits the key entirely and the Go `*bool`'s `nil` leaves the column alone — a stale display cannot become a stale write. The earlier entry here (*"can only be set through the API — no portal control writes it"*) is **closed**: the control landed in `ServerList`'s create/edit mask, on both paths, with the same authorization the backend enforces (plain server-update — no `isAdmin` gate, unlike the owners field beside it). See [the runtime chapter §11](cross-cutting/agent-runtime-manager.md#11-the-portal-admin-surface). |
| **`Service.UpdateMapping` is a read-modify-write with no compare-and-set, so two portal writers on one mapping lose an update** | `gateway/backend/internal/portal/service_applications.go` loads the row, applies the supplied pointer fields and writes the **whole struct** back. With two PATCHes in flight the later writer's full-row write reverts the earlier writer's field **even though it never sent that key** — no error, no 409, and no column on either screen that contradicts it. | **Pre-existing, and not introduced by the mapping/spec split**: the same read-modify-write has always backed `MappingSection`, where two browser tabs on one model reach it. What changed is the *exposure* — an agent-managed application's **model-mapping tab** and its **launch-spec form** are now a designed workflow with two mapping writers on one row ([agent-runtime-manager §11.4](cross-cutting/agent-runtime-manager.md#114-which-screen-owns-which-field)), while the set of fields both screens send shrank from three to **zero**. Be exact about what that buys: **field omission removes the routine clobber, not the race.** A form that never carries the other screen's field cannot overwrite it on *every* submit; two simultaneous PATCHes still lose an update regardless of which keys each one names. The comments at both call sites (`RuntimeAdminSection.submitEdit`, `RuntimeAdminSection.saveMappingFromTab`) and on `MappingForm`'s `appNameReadOnly` say exactly that — **do not restore an older wording that claims the split makes the two screens non-racing**, and do not read the body-shape tests as lost-update coverage. **Narrowed by issue #65, one class closed:** the portal edit no longer wide-writes the row. `Service.UpdateMapping` calls `UpdateMappingEditable`, which always writes the operator columns but writes each machine-owned metric column (and its `metrics_source`/`metrics_updated_at`) **only when the request supplied it** — a per-column `COALESCE(?, col)` fed a NULL for an unsupplied metric, no full-row round-trip — and `MappingForm` diffs its eight metric fields against their seed so an unchanged one is omitted. So an operator save that did not touch a metric can no longer revert a value a **background probe/benchmark** wrote while the form was open, on *either* channel (the stale struct or the always-submit body). What is NOT closed is the general two-portal-writers-**same-column** race: if both writers name a column, the later still wins with no CAS. The full fix is still a precondition on the endpoint (`If-Match`, or a version column checked in the `UPDATE`), a **backend contract change** deliberately not made here. Mitigating in the meantime: the window is one HTTP round trip, both writers are normally the same operator, and the two screens are two tabs of one component that share a single copy of the mapping list, so an interleaving needs two browser sessions rather than two clicks. |
| **`transport=websocket` together with `runtime_source=file` puts two writers on one WebSocket connection** | `Driver.Sync` posts the file-mode runtime report from the goroutine `triggerRuntimeSync` spawns, while telemetry, system reports and runtime logs are written from the agent's run loop. Nothing is corrupted — coder/websocket serializes frames internally — but the two contend for that internal write lock, and a write that waits out its 10 s `writeTimeout` there fails and calls `dropConn`, tearing down a healthy connection. The cost is a spurious reconnect, not data loss. | Accepted for now, and **reachable**: `main.go` installs the `WSSender` as the `RuntimeReporter` regardless of source, and `Config.validate` (`server-agent/internal/config/config.go`) does not check the two settings against each other, so the pairing is supported rather than rejected. The fix is to move the file-mode report onto the run loop the way `WSSender.resendRuntimeReport` already is; that is a behaviour change, and it was deliberately not made on the branch that found it. It was recorded **only** as a comment on `WSSender.PostRuntimeLog` (`server-agent/internal/client/ws.go`) until this entry — the same comment corrects an earlier, false "exactly one writer per connection" claim, so do not restore that claim from any older copy. |
| **`ProxyExcluded == true` implies `ProxyListenPort == 0` has no store-level backstop** | The violating row is a silent **total outage**, not an inconsistency: `routing.ApplicationEndpoint` composes `https://<domain>:<port>` and routes there, while `isProxySwitchCandidate` is false — so `AgentProxyRoutes` publishes no route, the agent opens no listener on that port, and `HTTPSSwitchUnreachableApps` structurally cannot name the row, because its filter starts with the candidate predicate. Nothing reports it, and nothing repairs it short of a later scope exit. | The state is **reachable only by a direct store write**, and only because one enforcement point holds: `applyProxyExclusion`'s **rule 4** (`gateway/backend/internal/portal/service_applications.go`), called last in the mutation block of `CreateApplication` and `UpdateApplication`. Rule 4 tests the **post-mutation** state — refusing with 409 `application.proxy_excluded_port_conflict` when the same request named a non-zero `proxy_listen_port`, clearing the stored port otherwise. It exists because rules 1–3 each branch on the **shape of the request** while the invariant is a property of the **resolved row**, so two ordinary PATCHes (`{proxy_excluded: true}`, then `{proxy_listen_port, scheme}`) reached the violating state through the public API until it landed. **Do not fold rule 4 back into the arms above it, and do not restore the pre-fix claim that the shape-branching rules were sufficient.** Unlike the `server_agent` row above, there is **no** backstop behind this one on any driver: migration 70 adds `proxy_excluded integer not null default 0` with **no CHECK, index or trigger**, and `routing.MemoryStore` carries the field inside a by-value `Application` with no locked check. The one other writer of a non-zero port — the lazy assignment in `AgentProxyRoutes` — is safe by the candidate predicate rather than by a check of its own, so a future caller that assigns a port outside that predicate reopens this. `revertScopeExit` is the only repair path, and only if that server later leaves https-switch scope ([certificates-tls §7](cross-cutting/certificates-tls.md#7-automatic-https-switch-of-applications), [ADR-030](09-architecture-decisions.md#adr-030--proxy-participation-is-an-operator-owned-flag-with-a-port-invariant-not-an-encoding)). |
| **Windows per-process VRAM rests on a display-driver DDI Microsoft never promised to applications, and on a counter Microsoft documents as able to over-report** | Two separate exposures behind one number ([ADR-031](09-architecture-decisions.md#adr-031--per-process-vram-on-windows-pdh-counters-plus-a-d3dkmt-luid-bridge), [agent-runtime-manager §5.3](cross-cutting/agent-runtime-manager.md#53-unknown-vram-resolves-itself-by-measurement)). **(a)** The LUID → PCI step calls the **D3DKMT** entry points, and the exposure is narrower and better evidenced than an earlier revision of this row claimed. `D3DKMTOpenAdapterFromLuid` and `D3DKMTQueryAdapterInfo` are ordinary **WDK DDI reference** pages under `windows-hardware/drivers/ddi/d3dkmthk/` — `ms.topic: reference`, `api_type: DllExport`, `Library: Gdi32.lib`, `DLL: Gdi32.dll` — and each states a **minimum supported client** (Windows 8, and Windows Vista / WDDM 1.0 respectively), which is Microsoft's normal compatibility signal. Neither page carries a stability or support disclaimer. What remains true is that this is *display-driver* DDI, addressed at drivers and low-level graphics clients rather than at applications: it is not part of the app-facing Win32 surface most applications target, and no Microsoft statement undertakes to keep it working for application use — so a Windows build that changed or withdrew it would break nothing Microsoft had promised. **Do not restore the earlier wording**, which placed these two functions in a "`devnotes` tier" and attributed a no-application-compatibility disclaimer to Microsoft; both pages were fetched and neither says either thing. Microsoft *does* document a low-level graphics client surface under `windows/win32/devnotes` — the "Graphics Low-Level Client Support" page, which opens with exactly such a warning ("These functions are subject to change with each operating system revision") — but the entry points it lists are the older `Dd*` / `NtGdiDd*` DirectDraw and Direct3D 8.x thunks, and no D3DKMT function appears on it. **(b)** Microsoft **KB4490156** documents that the `GPU Process Memory` performance counters can **over-report** a process's usage. | Both degrade in the harmless direction, by construction rather than by luck. Every export is resolved **up front** in the measurer's constructor, so a withdrawn or renamed one yields **no measurer at all** (the manager falls back to the operator's `vram_estimate_mb`) instead of a `LazyProc` panic inside an admission decision; a runtime failure never yields a wrong number, and its blast radius differs by half ([§5.3](cross-cutting/agent-runtime-manager.md#53-unknown-vram-resolves-itself-by-measurement) carries the detail): a **PDH** error yields `nil` for the whole cycle, while a **D3DKMT** error costs only its own adapter — that LUID is skipped, the rest are still measured, and the cycle yields `nil` only when *no* adapter resolved — with a transient failure asked again next cycle rather than remembered; and a returned PCI address outside PCI's own ranges (bus 0–255, device 0–31, function 0–7) is rejected, because a confident wrong address could join to the wrong GPU. An **over-report** charges a model more VRAM than it holds, which makes admission refuse or evict *earlier* than necessary — conservative, never an admitted OOM — and it did not appear on the probe host, where per-GPU totals agreed with `nvidia-smi memory.used` to within 0.04–0.8 %. What an operator sees if either bites: models that will not co-reside, or `vram_measured_mb` staying empty; in both cases `vram_locked` plus an operator estimate is the override. |
| **A llama.cpp build that rejects unknown top-level keys on `/v1/responses` turns the live-timings opt-in into a 4xx for the FIRST request per serving mapping per memo TTL** | With `responses_live_timings_enabled` on, the gateway adds `timings_per_token` to a streaming Responses passthrough body and does **not** retry without it, so a rejecting upstream fails that client's request rather than merely omitting a display figure. It is no longer every request: a 400/422 answered to a body the gateway injected into is recorded in the provider's negative-only rejection memo, so both endpoints stop asking that mapping for 5 minutes, and it is announced at **Warn** — on at the default log level — naming the `route_id`, the status, and that nothing was retried. The bound is per mapping per TTL rather than absolute: the record is written only once the upstream response arrives, so a client fanning out concurrently against one mapping takes a 4xx per in-flight request before the first refusal lands, and the memo is in-process, so a restart re-arms the cost for every mapping. Two cases never heal at all: a target with an empty `RouteID` is never memoized (probe- and benchmark-built targets, which do not serve client traffic), and a provider whose client lacks the optional memo seam records nothing | Accepted and bounded. The build this was measured against answered an entirely fabricated top-level key with an ordinary completion, and llama.cpp's request schema is pull-based, so a key nobody asks for is never inspected. The blast radius is one application, and the operator switches the flag off on whichever surface owns the endpoint — for a `server_agent` model that is the model's **runtime spec**, whose stored value the resolver takes over the parent application's whenever a spec exists, and the application form offers no switch for that type at all; for any other application it is the application itself. The failure is immediate and visible rather than silent, and now default-visible: the Warn line above is what makes it diagnosable, because the payload capture shows the client's bytes and not the body that was sent, and `proxyNative`'s per-request `timings_per_token_injected` field rides a **debug** line that a default deployment does not print ([Telemetry, Usage & Observability §8.4.3](cross-cutting/telemetry-usage-observability.md#843-running-connections-active-requests)). A retry remains a self-contained follow-up rather than something this design builds — the status is known before the first client byte and the untouched client bytes are still in hand — but the case it was wanted for is now bounded by the memo rather than unbounded, so it buys one request per mapping per TTL. |
| **`CostBudget` does not bite for a non-token request on a Tier-3-only host** | An image or audio request whose server offers neither power telemetry (Tier 1) nor a configured `estimated_watts` (Tier 2) is stamped `unpriceable` with 0 Wh, so it contributes 0 to the price-weighted cost `UsageAggregateSince` sums — a principal can exceed a `CostBudget` in substance while the budget reads as untouched. `RequestQuota` still applies; `TokenQuota` structurally cannot (`total_tokens` is 0 by the XOR) | **Set that server's `estimated_watts`.** Tier 2 is time-based and concurrency-shared, so it prices every endpoint kind at once, dimensionally honestly, with no new column and no per-unit coefficient — a one-field change on the server form. Synthesizing a token count instead is forbidden ([ADR-041](09-architecture-decisions.md#adr-041--a-billable-measure-is-a-unit-quantity-pair-never-a-scalar)); a quota denominated in `billing_quantity` is a missing capability, not a bug, and is owned by issue #119 ([§11.4](#114-deliberate-design-acceptances)). Also note the figure is honest, not merely absent: an `unpriceable` row says so on its `energy_source`, rather than reading as a measured zero ([Telemetry, Usage Analytics & Observability §8.4.4](cross-cutting/telemetry-usage-observability.md#844-energy-attribution)) |
| **A benchmark pass that returns no output keeps the mapping's old generation rate** | Keep-last in `UpdateMappingBenchmarkMetrics` leaves a stored generation rate in place when a pass yields no text. A model that stopped producing output keeps passing a group's speed floor (`filterBySpeedFloor`, `internal/routing/resolver.go`) until a pass measures it again, and only the run's history row shows the 0 | Accepted. A 0 is never a measurement, and the history row records the pass. Whether a pass with no text is a failed benchmark is a separate question ([Routing & Model Selection §7](cross-cutting/routing-and-model-selection.md#7-model-selection-metrics)) |
| **If the gateway dies between the VRAM benchmark's drain and its restore, every model on that server stays `force_stopped` until the gateway starts again** | The run force-stops **every** enabled launch spec on the server — the target included — and restores them in a `defer`. A gateway crash, a container restart or a `SIGKILL` inside that window leaves the whole fleet refusing to start, with nothing on the box to notice: `force_stopped` is a persistent override in the gateway document, so the agent keeps honouring it until the gateway clears it at its next start, and the run that wrote it is gone ([agent-runtime-manager §11.6](cross-cutting/agent-runtime-manager.md#116-the-vram-benchmark-load-one-model-alone-and-measure-what-it-costs)). | Reduced to a **recoverable-and-named** state rather than solved. Four things do the reducing, and none of them closes the window: the run **refuses to start** against any pre-existing override, so the state to restore is always exactly `""` and an operator clearing overrides by hand can never destroy a setting of their own; the result carries `drained_spec_ids`, so the portal can name the exact fleet that needs clearing; the restore runs on a context **derived from but not cancelled with** the run's, so an ordinary cancellation or error still restores — only process death does not; and the drain is recorded in the benchmark override lease (`benchmark_override_lease:<server_id>`) before the write, so the gateway clears exactly those overrides by compare-and-set when it starts again ([ADR-047](09-architecture-decisions.md#adr-047--a-manual-speed-run-measures-every-agent-model-on-an-emptied-server-it-stops-the-servers-running-models-before-each-cold-pass-and-lifts-the-servers-pins-for-the-run)). So process death leaves the fleet `force_stopped` only until the gateway is back, not until an operator notices. The deferred agent-side "measure now, isolated" capability is still the only design with no window at all, because the agent both owns and restores its own transient state. **Do not describe the `defer` as the mitigation** — it is what makes the ordinary paths safe and is exactly what a crash skips. **The applied-document acknowledgement narrows the window but does not close it, and the distinction matters to anyone re-reading this row.** Against an agent declaring `runtime_config_ack` the isolation is proved as soon as the agent reports having applied the drain document — normally one telemetry interval — instead of after an unconditional 60 s wait for its poll ([agent-runtime-manager §11.6](cross-cutting/agent-runtime-manager.md#116-the-vram-benchmark-load-one-model-alone-and-measure-what-it-costs)), so the *minimum* time the fleet spends force-stopped, and therefore the crash window, drops by about a minute per run. What is unchanged: the exposure is still bounded by the whole measurement (two stability windows plus the model's own load, by far the longest part), an agent that does not declare the name still pays the full 60 s, and **process death anywhere in the window still leaves every override in place** — nothing about proving that a document arrived helps a gateway that is no longer running to withdraw it. So do not read the acknowledgement as a partial fix for this row; it shrinks one summand of the window's length and addresses a different defect entirely (a run that reported an isolation it had not earned). |

## 11.2 Design tensions to respect

- **CGO-free build vs. richer native libraries.** The static, CGO-free build
  forbids CGo-only dependencies. Server-side image transcoding (e.g. HEIC via
  libvips/libheif) would reintroduce CGo — HEIC is handled client-side instead.
- **Two enforcement surfaces.** The public and mesh listeners must be kept
  independent; per-listener behavior is threaded through request context rather
  than inferred, to avoid one surface's assumptions leaking into the other.
- **Reconcile vs. transient errors.** Reconcilers must distinguish a transient
  dependency error (keep current) from a definitive empty result (tear down);
  getting this wrong strands or destroys healthy resources
  ([ADR-022](09-architecture-decisions.md#adr-022--reconcile-loops-keep-healthy-resources-on-transient-errors)).
- **Conditional role-scopes.** Authorization flags must be read from an
  always-present role-scope; making a scope conditional (e.g. step-up) can break
  self-service paths that read it as a flag
  ([ADR-021](09-architecture-decisions.md#adr-021--layered-rbac-with-delegation-and-step-up)).

## 11.3 Testing blind spots to remember

- The memory/in-memory driver does not enforce foreign keys and has no usage-event
  store; FK-violation and usage-aggregation bugs are invisible there — test those
  paths against SQLite/PostgreSQL and via the store conformance suite.
- A nil Go slice in a DTO marshals to JSON `null` and can crash a TypeScript
  frontend; list DTO fields should be initialized to empty slices, and real
  backend↔frontend end-to-end coverage catches what unit tests and mocks mask.
  Two shapes produce nil where the author expected empty and need explicit
  guards — `append([]T(nil), src...)` when there is nothing to append, and
  `json.Unmarshal([]byte("null"), &m)` — and a conformance assertion must test
  `x == nil` explicitly, not merely `len(x) == 0`, or it cannot see either.
- **Only `e2e:runtime` runs in CI; every other Playwright scenario suite is
  local-only**, so a pull request can still pass without them; the e2e fixture
  Go modules are likewise outside `make lint`, `make test-go` and Sonar's
  sources. See
  [Development Tooling & Quality Gates §6](cross-cutting/development-and-quality.md).
- **No gate in this repository can see a browser-engine-specific layout defect.**
  The frontend Vitest suite runs in `jsdom` (`gateway/frontend/vite.config.ts`,
  `environment: 'jsdom'`), which performs no layout at all, and no Playwright
  config under `gateway/e2e/` declares `projects`, `browserName` or `devices`, so
  every scenario suite runs in the default Chromium. A defect that exists only in
  another engine is therefore invisible to every gate at once. This is not
  hypothetical: the co-residency matrix shipped multi-line column headers that
  overlapped their neighbours in **WebKit only** — WebKit does not contribute a
  `writing-mode: vertical-rl` child's block size to its table column, so the column
  never widened, while Chromium and Firefox were correct. It reached an operator on
  Safari, and the code comment asserting the opposite had genuinely been measured —
  in Chromium. See
  [Agent-managed model runtime §11.3](cross-cutting/agent-runtime-manager.md).
- **A comment that names a collaborator or asserts a cross-layer guarantee is a
  claim to verify, not documentation** — several have shipped false, and a
  guarantee that differs per driver must be stated per driver. The instances and
  the corollary ("no test can fail on this line" is an invitation to delete a
  load-bearing guard) are in
  [Development Tooling & Quality Gates §9](cross-cutting/development-and-quality.md).
- **CI compiles nothing for Windows**, although the gateway ships `windows-amd64`
  and `windows-arm64` agent binaries. Every job in `.github/workflows/ci.yml` runs
  on `ubuntu-latest` with no `GOOS` set, so `proc_windows.go` and every
  Windows-only behaviour are unbuilt and untested. This document previously
  claimed the opposite, and that false claim is part of why a whole defect class
  went unnoticed: **a case-sensitive guard in front of an OS API that is
  case-insensitive on Windows**. Two shipped —
  `${AGENT_ENV:op_agent_token}` slipped past the agent's own-namespace refusal
  because `GetEnvironmentVariableW` resolves case-insensitively, and a spec env
  key spelled `Path` slipped past the `PATH`/`HOME` reservation and then won
  `os/exec`'s case-insensitive deduplication. Both are fixed by folding case at
  the guard, and both are tested on any host via the injectable `getenv` seam.
  Until CI grows a Windows step, `GOOS=windows GOARCH={amd64,arm64} go vet ./...`
  is the check, and it belongs in any review that touches path handling,
  environment variables, filenames, or process control. In the same vein, the
  `runtime_allowed_dirs` containment check (`withinDir`) is Windows-native —
  backslash separators, drive letters, UNC, case — and CI executes it only on
  POSIX. The wildcard entry added for `<dir>/*` reduces to a pure,
  GOOS-independent string step (`allowedDirBase`, tested on Linux with
  Windows-shaped inputs) and hands the untrusted work_dir to the unchanged
  `withinDir`, so this branch adds no new *Windows-native* code path — but the
  containment itself, being security-adjacent, stays proven only by out-of-band
  Windows-semantics testing, not by CI, until that Windows step exists.
- **The Windows VRAM measurer's syscall layer is the largest body of code no
  gate in this repository executes**, and the shape of that code is a direct
  response to it. `collector/nvidia_pdh_windows.go` (~600 lines of PDH and
  D3DKMT calls, `unsafe` struct mirrors and pointer arithmetic) is never built
  on `ubuntu-latest`, so it is covered by exactly three things: **compile-time
  struct-layout assertions** that make a wrong size, offset or field width fail
  `GOOS=windows go build ./...` on any host, a runtime plausibility gate on the
  PCI address the kernel writes back, and whatever a developer runs on a real
  Windows box. That is why **everything that can be wrong about a number** — the
  counter-instance grammar, the `pci.bus_id` grammar, the byte→MB arithmetic,
  the multi-segment summing, the drop of a measured `0`, and the LUID-cache
  decisions — lives in the build-tag-free `collector/nvidia_pdh.go`, where a
  Linux unit test exercises the very code Windows runs
  ([agent-runtime-manager §5.3](cross-cutting/agent-runtime-manager.md#53-unknown-vram-resolves-itself-by-measurement)).
  **The split is a rule, not an accident of authorship, and it has already been
  earned once:** the LUID resolution started out inside the Windows file and
  permanently negative-cached perfectly good GPUs after a single `nvidia-smi`
  timeout — a defect whose only symptom is a measurement that silently never
  arrives, found by review because nothing else could look. A *decision* belongs
  in the tag-free half even when only Windows reaches it; what the build tag is
  for is the syscall.
- **"Pre-existing" means present on `main`, never "present at an earlier commit
  of this branch".** A finding on the agent-managed runtime was dismissed as
  pre-existing at an intermediate commit of its own feature branch — for a
  package that does not exist on `main` at all, so nothing about it could be
  pre-existing. The refutation was sound about the change it examined and wrong
  about the baseline, and the finding (an unbounded fork-exec loop) survived a
  further review round because of the label. Verify with
  `git show main:<path>`, and state the commit you checked.
- **Concurrency defects need concurrent tests, and a scenario suite that issues
  its requests sequentially cannot see them.** The same fork-exec loop was
  reachable from two ordinary inference requests for different models, yet the
  e2e scenarios that exercise exactly those two models passed, because they issue
  the two requests one after the other. When a rule is about admission,
  eviction, locking or generation identity, the covering test has to overlap the
  requests in time.
- **`agentFeaturesRegistry` is a `Retain`-pruned per-server registry.** It is in
  `cmd/gateway`'s prune bundle alongside `runtimeStatusRegistry`, and a
  mutation-proof wiring test pins that both sides hold the same instance — but the
  trap it was built to avoid is silent: an unexported constructor lets
  `gateway.New` default-construct an instance `cmd/gateway` never sees, so a
  correct `Retain` runs against the wrong object and prunes nothing, with
  everything compiling and the prune apparently running.
- **`npm test` does not type-check, so a green frontend suite says nothing
  about the build.** `npm test` is `vitest run`; only `npm run build` runs
  `tsc`, which is why CI runs both
  ([Development Tooling & Quality Gates
  §5](cross-cutting/development-and-quality.md)). The failure this hides is not
  exotic: a test helper typed as a wide store or props object — `ChatStore`'s
  `makeStore` in `ChatSidebar.test.tsx` enumerates every field with no cast —
  stops compiling the moment that type gains a field, while the suite it
  belongs to still passes. Any change that widens such a type must be verified
  with `npm run build`, not with `npm test`.

## 11.4 Deliberate design acceptances

These structures were reviewed against SOLID/SoC/DRY/KISS/coupling principles
and **deliberately kept as they are**. They are decisions, not oversights —
recorded here so they are not re-litigated (or "fixed") without new evidence.

| Structure | Decision & rationale |
|---|---|
| **`internal/store/migrate.go` as one append-only file** (94 migrations and counting) | A legitimate ledger: clean runner, documented `rawUp` escape hatch, well-commented entries. Splitting per-version would churn history for no changeability gain. New columns use `addColumnIfMissing`; the baseline is frozen (no back-porting — fresh installs replay the full chain). |
| **`gateway.Server` as one type** | Splitting the type would be high-risk for little gain (nil-safe-registry convention, in-package tests). Cohesion is managed instead via per-feature *files*, named sub-structs for field clusters, and the generic `settingCache[T]`/`warnThrottle` helpers. |
| **`portal.API` (generated) and `routing.Store` as wide facades** | `portal.API` is interfacer-generated from `portal.Service` and stays whole; `routing.Store` is a composition of role sub-interfaces but keeps the full embedding for existing consumers. Narrowing happens **consumer-side** (e.g. `resolverStore`, `PrincipalLimitStore`, `agentIngestPortal`/`certPortal`/`settingsPortal`). Note: the `interfacer` regeneration of `api.go` is broken (self-import bug) — signature changes are hand-edited there; only `api_tracing_gen.go` regenerates via `go generate` (gowrap). |
| **i18n as TypeScript modules, not JSON resources** | JSON would forfeit compile-time key parity and cannot carry function-valued messages. `PortalMessages = typeof de` keeps the compiler enforcing exact de/en parity. |
| **No generic CRUD/dialog hook in the portal frontend** | The views' mode/confirm shapes legitimately diverge (string-id vs object targets, 2–10 modes); one API would invalidate large test suites for little gain. Shared pieces exist where they are truly identical (`listTableLabels`, `ModelOverrideEditor`, `AdminGroupPicker`/`Editor`, `useColumnSettings`, `useLatestFetch`/`usePolledFetch`). |
| **`LineChart` and `UptimeTimeline` stay separate** | ~20 shared lines vs fundamentally different hover models; a shared chart scaffold would be a leaky abstraction. |
| **Two atomic-file writers in the server-agent** (`trust` vs `certinstall`) | Different semantics by design: single-file backup/rollback + `os.Root` validation vs staged multi-file batch. Cross-referenced in doc comments, not merged. |
| **`Activity`'s bespoke SSE guard machinery** | Its asymmetric bump-and-release protocol is unique; forcing it into the shared fetch hooks would complicate both. It lives isolated in `useActivityData`. |
| **The routing scorer** | The viability gate before the bounded tiebreak is structural and test-guarded; adding a scoring term is a local change (shared `scoringRoute` constructor feeds both real routing and the UI ranking). |
| **`agentDNS` cache separate from `settingCache[T]`** | It deliberately holds its mutex across the resolve to single-flight concurrent NetBird lookups; the generic cache releases the lock during load. |
| **Agent-listener state machine in `cmd/gateway/agent_listener.go` (package main)** | Deliberately not an `internal/` package: no second consumer exists, and its tests depend on a NetBird test fixture shared with the sync loop's tests. Promote only when a concrete reuse appears. |

| **A speech reply is held whole in memory by the executor and, per mounted turn, by the browser, and the playback fetch guard is a literal prefix** | The executor reads the WAV whole (it is not bounded by the capture cap, because a clip cannot be played from a prefix), so each in-flight speech run holds its whole response, bounded in the end only by the store's per-blob ceiling (`MaxChatBlobBytes`, 20 MiB), whose refusal ends the run `gateway.chat_run_commit_failed`; a WAV is uncompressed, so a long text can approach it. | **A portal transcription clip is converted to WAV in the browser, and that conversion has four accepted costs** (the earlier acceptance — relayed in the recorder's native container, audio.cpp not yet confirmed to decode it, conversion deferred — is **RESOLVED**) | **Resolved: the conversion shipped.** The first design relayed the recorder's container as recorded, recorded as an open item whether audio.cpp decodes anything but WAV, and named a client-side conversion as the way forward if it did not. A live probe of a live audio.cpp server (2026-10-18) showed it reads **WAV only**: a `webm`, `ogg`, `m4a` or `mp3` upload is answered 400, "only WAV audio uploads are currently supported for transcription; MP3 support is planned". So the composer now **converts every clip, picked or recorded, to a 16 kHz mono 16-bit PCM WAV** (WebAudio decode, an `OfflineAudioContext` resample, a hand-written 44-byte header) before it enters the turn, which makes in-browser recording and any attached format the browser can decode work end to end; the gateway still transcodes nothing, and the project never re-encodes server-side ([ADR-064](09-architecture-decisions.md#adr-064--transcription-in-the-portal-chat-is-the-fourth-run-kind-the-model-is-the-affordance-the-audio-input-lives-in-chat_blobs-and-is-relayed-multipart-over-loopback-and-the-reply-is-the-ordinary-text-turn) (e), (h)). The blob allow-list's wider audio family (`audio/webm`, `audio/mpeg`, `audio/mp4`, `audio/ogg` beside `audio/wav`) is **kept deliberately**: the store is payload-type-agnostic, an exact-match allow-list of audio types is as safe as a narrow one, and upstream says MP3 support is planned, so a later composer that relays more than WAV needs no backend change; it simply is not exercised while the composer produces only WAV. **The costs accepted for converting in the browser:** (1) **Decode memory.** The browser reads the whole upload and decodes it to 32-bit float samples at the context's rate and the clip's channel count (about 0.4 MB per second of 48 kHz stereo) before the WAV is written, so a long compressed upload costs many times its size in memory; the 20 MiB ceiling bounds the upload and the finished WAV, not that intermediate buffer, and a device that runs out fails the attach rather than the send. (2) **No progress figure.** Decoding and resampling run to completion with no intermediate news, so the composer can show only an indeterminate "Converting audio…" indicator (a spinner and its label, with the attach, record and Send controls held) for as long as a long file takes, never a percentage or an estimate. The attaches are numbered and only the newest one lands, so overlapping or abandoned conversions cannot land out of order. (3) **Double resample.** The audio is resampled twice: `decodeAudioData` first resamples the decoded clip to the `AudioContext`'s device-dependent rate (typically 44.1 or 48 kHz, whatever the codec's own rate was), then an `OfflineAudioContext` resamples that to 16 kHz. The quality of each step is implementation-defined and differs between browsers; accepted because speech models run at 16 kHz anyway and the alternative is a hand-written or bundled resampler. (4) **Old Safari.** Before Safari 14.1, `decodeAudioData` takes callbacks only and returns no promise, so the conversion surfaces as the composer's "could not be processed" refusal rather than a transcript; no callback-form fallback is written for a browser that old. |

| **Streaming transcription has three accepted billing/timing nuances: a clean-cut stream reads as a billed-zero success, the first-byte grace is generous, and a WAV header can hide about 0.5 s of audio** | A streamed transcription has no response `audio_duration_ms` to bill from, so it is metered from the **uploaded WAV header** and only on a clean `transcript.text.done` + `[DONE]` completion ([ADR-065](09-architecture-decisions.md#adr-065--streaming-transcription-the-gateway-relays-the-sse-for-a-streaming-model-gated-by-a-transcription_streaming-verdict-with-a-retry-buffered-on-500-safety-net-bills-the-streamed-call-from-the-wav-header-and-the-portal-chat-run-streams-the-transcript), [Telemetry §8.4.1](cross-cutting/telemetry-usage-observability.md#841-the-usage-event)). Three consequences are accepted, not hidden. **(1) A stream that ends cleanly but without both terminal markers (an upstream that closed after a clean EOF without `[DONE]`) records a `success` usage row with `billing_quantity` 0 and an `Error` log line.** The usage UI reads a `success` row as "all good", so the Error log is where the zero is explained; this is the same loud-zero contract as the buffered path (ADR-041), surfacing in the usage views as a free-looking success until the log is read. The alternative — guessing a duration from a truncated stream, or marking the whole call failed after the client already has a transcript — is worse. **(2) The streamed relay's first-byte deadline grace is deliberately generous.** A cold `mode=streaming` model's time-to-first-token can be long, so the relay is bounded before the first byte by the **larger of** the application `timeout_ms` and the idle timeout (so a short idle timeout cannot cut a warm-up a long `timeout_ms` allows); when the idle timeout is disabled (`0`/negative) the relay is left **unbounded**, and only the portal run's own deadline bounds that path (a raw API client streaming with the idle watchdog off is then unbounded apart from its own disconnect, because the total `timeout_ms` arms only on the non-streaming path). **(3) The WAV-header billing has a bounded forgery residual.** The duration is the header's `data` size over its byte-rate, guarded from **both** directions: the uploaded bytes may not exceed the declared `data` size by more than about 16 KiB (audio **hidden behind a small or zero `data` chunk**, which would under-report the duration, is billed a loud zero — a header that declares *more* than the file holds, a truncated file or an oversized declaration such as the `0xFFFFFFFF` a streamed WAV carries, is no measurement either: it returns `(0, false)` and bills a loud zero, never the declared duration; that is the safe direction against over-billing, and it cannot become an under-bill, because audio.cpp refuses such a file: probed live against audio.cpp v0.9.1, a truncated file, a `data` size declared 1 MiB too large and `0xFFFFFFFF` all fail with HTTP 500 `failed to read WAV data chunk`, in a buffered request and in a `stream=true` request to a `mode=streaming` model alike, so the call never completes and no clip is transcribed for the zero; re-check this when audio.cpp is upgraded, since a build that decodes a short `data` chunk would turn the zero into an under-bill), and the `fmt` chunk must be self-consistent (`byteRate == sampleRate * blockAlign`, `blockAlign == channels * ceil(bits/8)`), so an inflated byte-rate cannot shrink the computed duration. What remains hideable is the trailing slack a real file can carry (about 16 KiB, ≈ 0.5 s at 16 kHz mono 16-bit, longer at a lower byte rate), and a consistently forged header is self-defeating because audio.cpp would mis-transcribe the clip the header describes. A non-PCM or unparseable WAV bills loud-zero. |
