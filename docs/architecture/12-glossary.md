# 12. Glossary

Domain and technical terms used throughout this documentation.

| Term | Definition |
|---|---|
| **OnPrem AI Gateway (OP AI Gateway)** | This product: a self-hostable AI gateway and management portal. |
| **Gateway** | The Go backend service (`op-ai-gateway`) that terminates client APIs, routes/dispatches inference, and serves portal/system/agent APIs. |
| **Portal** | The React/TypeScript SPA for administration and the chat playground, served under `/portal/`. |
| **Server-Agent** | The standalone Go binary (`op-ai-server-agent`) installed next to an AI server that reports telemetry, can terminate mesh TLS, and can manage the local model server processes. |
| **AI server** | A host running an inference engine (Ollama, llama.cpp, or vLLM) that the gateway dispatches to. |
| **Application** | A running inference endpoint on an AI server (type, port, scheme, API flavors, tuning fields). One AI server can have several. |
| **Model mapping** | The link between a public gateway model name and an application's model name; routing operates over **active** mappings. |
| **Model group** | A named, possibly nested grouping of models with a traversal strategy. |
| **Resolver** | The routing component that turns a model name + API flavor into candidate `(server, application, mapping)` tuples. |
| **Candidate scoring** | Ranking candidates by telemetry (load, latency, error rate, availability), priority/weight, and capacity. No capability verdict takes part: the scorer sees measurements, priority and weight, and nothing else. |
| **Required capability** | A capability name an **endpoint** demands of any model that serves it, carried on `inference.Request.RequiredCapabilities` and set from the endpoint's own identity, never from the request body. Empty for chat/Responses/Messages; `image` for `/v1/images/generations`; `image_edit` for `/v1/images/edits`; `speech` for `/v1/audio/speech`; `transcription` for `/v1/audio/transcriptions`. It is the gateway's only *excluding* capability check: a mapping without a `yes` verdict for every required name is not a candidate, an absent verdict refuses, and a store error refuses ([ADR-042](09-architecture-decisions.md#adr-042--the-images-gate-keys-on-a-required-capability-and-an-absent-verdict-refuses)) — except that `image_edit` is **derived** (see below) rather than read from a row. |
| **`image_edit` (derived capability)** | Whether a model may be handed an image to edit. Not probed and not stored as a verdict: `routing.ImpliedImageEdit` is true for a mapping with an `image: yes` verdict **unless** an operator set an `image_edit: no` row on it (the opt-out; an `image_edit: yes` row is inert). One function read by the routing gate, the unknown-model redirect and the portal listing's `image_edit` flag; an agent may not report it ([ADR-057](09-architecture-decisions.md#adr-057--image-edit-a-derived-image_edit-capability-a-multipart-passthrough-and-the-attached-image-as-the-edit-affordance)). |
| **`multipart_proxy`** | An agent feature flag (agent 0.9.0): the agent's runtime router finds the child to start from the `model` part of a `multipart/form-data` body. The gateway refuses an image edit (404 `images.edit_unavailable`) or an audio transcription (404 `transcription.unavailable`) to an agent-launched model whose agent has not declared it, fail-closed. |
| **`speech` capability** | Whether a model **synthesises** speech, and so may be the target of `POST /v1/audio/speech` (`routing.CapabilitySpeech`). Orthogonal to the `audio` capability, which means the model **accepts** audio input (a llama.cpp `/props` modality): the two can co-occur and neither is ever mapped onto the other. It is also not the billable unit (`audio_second`), unlike `image`. The gateway's health loop writes it for an `audio_cpp` application from audio.cpp's `/v1/models` `task` (`tts` or `clone` is `yes`, any other task `no`, an unlisted model nothing), as the `audiocpp_models` source; `(speech, no)` is reserved against a manual write ([ADR-061](09-architecture-decisions.md#adr-061--speech-is-the-second-endpoint-on-the-capability-gate-a-distinct-speech-capability-a-coarse-openai_audio-flavor-the-audio_cpp-kind-and-a-binary-relay-that-serves-wav-only)). |
| **`transcription` capability** | Whether a model **transcribes** audio to text, and so may be the target of `POST /v1/audio/transcriptions` (`routing.CapabilityTranscription`). Orthogonal to both `audio` (the model **accepts** audio as chat input) and `speech` (the model **synthesises** speech): the three can co-occur and none is ever mapped onto another. Like `speech` it is not the billable unit (`audio_second`). The gateway's health loop writes it, from the same audio.cpp `/v1/models` `task` as `speech` and as the `audiocpp_models` source: `asr` is `(transcription, yes)` and `(speech, no)`, `tts` or `clone` the reverse, any other task `no` for both, an unlisted model nothing. `(transcription, no)` is reserved against a manual write, and the name is **not** reserved against an agent report; an agent-launched `audio_cpp` child has no automatic verdict yet (deferred), so an operator's `transcription: yes` serves it. It has no portal fold, so it neither feeds the unknown-model redirect nor appears as a listing flag ([ADR-062](09-architecture-decisions.md#adr-062--transcription-is-multipart-in-and-json-out-on-the-shared-openai_audio-flavor-a-distinct-transcription-capability-billing-read-from-the-response-body-and-every-divergence-from-speech-keyed-on-the-endpoint)). |
| **`audio_cpp`** | Two namespaces, one name, both for audio.cpp's `audiocpp_server`. As an **application type** (`routing.ProviderAudioCpp`) it is a static, operator-run server with no runtime spec, defaulting to `timeout_ms` 600000, the `openai_audio` flavor and the `/health` health path, and it is the type the health loop probes for the `speech` and `transcription` verdicts. As a **runtime spec kind** (`routing.RuntimeSpecTypeAudioCpp`) it is the agent-managed counterpart, detected from an `audiocpp_server`/`audio.cpp` binary, with no probe paths; its automatic verdict is deferred ([Agent-Managed Model Runtime §3.4](cross-cutting/agent-runtime-manager.md#34-runtime-server-kind-and-per-kind-probe-path-derivation)). |
| **`openai_audio` (flavor)** | The coarse API flavor of `POST /v1/audio/speech` and `POST /v1/audio/transcriptions` (`routing.APIFlavorOpenAIAudio`), `openai_images`' twin: a flavor of its own, folded by `NormalizeAPIFlavor` before the generic `openai` prefix, opt-in everywhere (an empty list still saves as `openai` + `anthropic`). An application listing `openai_audio` and neither text flavor is **audio-only** (`routing.FlavorsAreAudioOnly`): it is kept out of the chat flavors, listings and every job that sends a mapping a chat prompt, and the portal's mapping DTO marks it `audio_only`. The flavor is **shared** by the two audio endpoints, so it cannot say which a request is: whatever differs between speech and transcription (the upstream path, the source of the billing quantity, the upstream-error relay, the capture predicate) is keyed on the **endpoint**, and the model's `speech` or `transcription` verdict says which it serves ([ADR-062](09-architecture-decisions.md#adr-062--transcription-is-multipart-in-and-json-out-on-the-shared-openai_audio-flavor-a-distinct-transcription-capability-billing-read-from-the-response-body-and-every-divergence-from-speech-keyed-on-the-endpoint)). |
| **`audio_second` (billing unit)** | The billable unit of a speech or a transcription request (`usage.BillingUnitAudioSecond`): `billing_quantity` is seconds of audio, and every token column and rate is `0`. A speech request's quantity is the audio **produced**, read from the upstream's `X-AudioCPP-Audio-Duration-Ms` header divided by 1000; a transcription's is the audio **transcribed**, read from the response **body**'s `timing.audio_duration_ms` divided by 1000 (audio.cpp sends no header there). A success with no usable duration records `0` and is logged at `Error`. The live Active Requests row carries the unit too (`billing_unit`), so a non-token request shows an em dash instead of a token count. |
| **`image` vs `vision` capability** | Orthogonal axes, never folded together: `image` means the model **generates** images, `vision` means it **accepts** them. A model may carry both, either or neither. A generator that is handed an image as the **source of an edit** is a third thing, `image_edit` (derived from `image`, above), and the portal's attach control reads it on an image thread, never `vision`. |
| **MTP (Multi-Token Prediction)** | A property of the model's **weights**: the checkpoint ships an extra head able to propose more than one token at a time (DeepSeek-V3, GLM-4.5/4.6). The `mtp` capability verdict makes exactly this claim, name-guessed or operator-stated, and is display and operator-seed only. It is *not* evidence that the endpoint serving the model is drafting anything ([ADR-040](09-architecture-decisions.md#adr-040--the-flat-mtp-bonus-is-deleted-mtp-splits-into-a-declared-trait-and-an-observed-one)). |
| **Speculative decoding / drafted tokens** | A property of the **deployment**: the running inference server proposes tokens with a draft model or head and verifies them in a batch, which is what can make it faster. Observed, never assumed — llama.cpp reports `timings.draft_n` on a completion it has served, and the `speculation_observed` verdict records that this gateway saw it happen on that mapping. Absence of the verdict is unknown, never a negative ([ADR-040](09-architecture-decisions.md#adr-040--the-flat-mtp-bonus-is-deleted-mtp-splits-into-a-declared-trait-and-an-observed-one)). |
| **Route affinity** | Sticky routing keyed on application/server (per token/user, with a TTL). |
| **Generated Claude alias** | A per-token, computed second name `anthropic-local-<12 hex>` (SHA-256 of the gateway model or group id) for an eligible local model or group, enabled by the token setting `claude_model_aliases`. It is listed beside the real id with `original_model_id` and an honest `display_name`, and resolved once to the real target, so that Claude Desktop and Claude Code, whose client-side id filter rejects some family names, can select local models ([ADR-058](09-architecture-decisions.md#adr-058--claude-model-aliases-are-computed-per-token-from-one-shared-derivation-hashed-over-the-gateway-id-and-carried-as-sibling-metadata)). |
| **Claude Code effort compatibility** | A per-token opt-in (`claude_effort_compatibility`, default off, management-only to set) that makes Claude Code's `output_config.effort` reach Qwen on llama.cpp or vLLM as `chat_template_kwargs.reasoning_effort`, the only field the chat template reads, on both native `/v1/messages` passthrough and translation, forwarding the level verbatim and doing nothing on any other backend ([ADR-059](09-architecture-decisions.md#adr-059--claude-code-effort-is-delivered-as-a-chat-template-kwarg-on-both-paths-for-llamacpp-and-vllm-and-is-a-management-only-token-setting), [API Compatibility & Inference §9.2](cross-cutting/compatibility-and-inference.md#92-claude-code-reasoning-effort-compatibility)). |
| **Model override rule** | A per-token row `requested name -> {to, offer, hide_target}`: rewrite this requested name to `to`, optionally advertise the requested name in this token's listing (`offer`) and drop the target's own name from it (`hide_target`). |
| **Unknown-model redirect** | A per-token opt-in: a requested model that does not apply is served by the token's last successfully routed model, then by a configured fallback, instead of failing. |
| **Offered / callable / existing** | The three model sets kept apart per token: what a listing shows, what a direct request can actually route to, and what exists at all. |
| **API flavor** | The client dialect: OpenAI-compatible, Anthropic-compatible, Codex (`/v1/responses`), Claude Code (`/v1/messages`), OpenAI image generation and edit (`/v1/images/generations`, `/v1/images/edits`, one coarse flavor), or OpenAI speech and transcription (`/v1/audio/speech`, `/v1/audio/transcriptions`, the one coarse flavor `openai_audio`). Candidacy matches the request's **coarse** flavor — `openai`, `anthropic`, `openai_images` or `openai_audio` — against the ones an application declares. Saving an empty list stores `openai` + `anthropic`, never images, speech or transcription; the default applies only on save, so an application whose list is stored empty is a candidate for no flavor at all. |
| **Provider** | A backend client **adapter** (Ollama, OpenAI-compatible for vLLM/llama.cpp, the native Anthropic Messages / OpenAI Responses / Google Gemini vendor clients, or the mock) — the dispatch-layer code that speaks an upstream's protocol. **Not** a vendor account: the word also names `Application.Type`, `Target.Provider` and `usage.Event.Provider`, which is exactly why the external-account entity below is named `vendor_account` instead ([ADR-049](09-architecture-decisions.md#adr-049--vendor-accounts-are-a-first-class-entity-the-subscription-oauth-path-is-experimental-and-tos-restricted)). |
| **Vendor account (Anbieter)** | An external AI vendor account a user connects to route requests through (their own, or, once the owner has **shared** it, those of the principals provisioned into a resource group that contains it): either a plain platform **API key** or an experimental consumer **subscription** (OAuth), for OpenAI or Anthropic, or (API key only) an **OpenAI-compatible** hosted provider — x.ai, OpenRouter, the Kilo Gateway, Google Gemini through its OpenAI shim, or a Custom endpoint — which carries an immutable `base_url` root and is a preset over the one OpenAI client ([ADR-052](09-architecture-decisions.md#adr-052--openai-compatible-vendors-are-presets-over-one-openai-client-a-stored-root-url-plus-a-registry-derived-path-prefix)), or **Google Gemini (native)** (`google_native`), a separate preset account served by the native `generateContent` client rather than the shim ([ADR-054](09-architecture-decisions.md#adr-054--native-google-gemini-dialect-its-own-vendor-id-and-provider-kind-selected-by-the-preset-dialect-field-over-a-leaf-translation-package)). Owned by exactly one user, personal by default, off by default behind a master flag, and distinct from both the **Provider** adapter above and the self-hosted **AI server**. See [External Vendor Accounts](cross-cutting/external-vendor-accounts.md). |
| **Share level (vendor account)** | `none` \| `shared` \| `full`: how far a vendor account is shared beyond its owner, and so how much a co-manager of it may do. `none` is a personal account (the default); only an owner who is an admin raises it. See **Shared** and **Full shared** below and [External Vendor Accounts §1.1](cross-cutting/external-vendor-accounts.md#11-share-levels). |
| **Shared (vendor account)** | A vendor account at share level `shared`: assigned to management groups and linked into resource groups. A co-manager may **operate** it (status, model prefix, rename, test connection, model refresh, usage refresh); the credential, the group and resource-group assignment, the delete and the lowering stay with the owner. A principal provisioned into a linked resource group may **route** to it once its token names it. A subscription account can be shared at most at this level, and even there its token-opening operate calls stay owner-only ([External Vendor Accounts §8.1](cross-cutting/external-vendor-accounts.md#81-the-matrix)). |
| **Full shared (vendor account)** | A vendor account at share level `full`: **complete owner-equivalent delegation**. A co-manager may do everything the owner can, the credential, the group and resource-group assignment, the delete and the lowering, except **raise** the level; the owner's control is structural (they own the record and can always lower it). Never available for a subscription account. |
| **Co-manager (CM) of a vendor account** | An owner or co-manager holding the `can_manage_vendor_accounts` permission of a management group a shared account is assigned to; the intersection is read live, so un-assigning the group or demoting the co-manager revokes the reach at once. A CM gets the management view (still no secret). |
| **Member (vendor account)** | A principal provisioned into a resource group that contains a shared account. It gets a minimal, allowlist-built, key-free read and may use the account once a token opts in; it never operates it. |
| **Management group / containment root (vendor account)** | The admin-tier groups assigned to a shared account (at least one while it is shared), and the one system group they must all sit under (`system_group_id`, immutable while the account is shared). The same containment rule AI servers use. |
| **Routing grant (vendor account)** | The routing-time rule that decides which accounts a principal can **reach**: owned, or live `shared`/`full` and linked to a resource group the principal is provisioned into. A pure, fail-closed grant, deliberately **not** the AI-server rule (no open pool, `resource_provisioning_enforce` not read); an unwired seam is owner-only. Reaching an account is not using it: that also needs the token's per-account opt-in ([External Vendor Accounts §4.6](cross-cutting/external-vendor-accounts.md#46-routing-to-a-shared-account-the-pure-grant)). |
| **Subscription (vendor account)** | The experimental, ToS-restricted auth type of a vendor account: consumer-subscription OAuth tokens (Claude Pro/Max, ChatGPT/Codex) reused for inference through the gateway, reverse-engineered and VERIFY-LIVE. The alternative auth type is the documented, metered API key. Independently switchable by the `vendor_subscriptions_enabled` system setting (default on): off refuses creating or connecting one and leaves existing ones kept but unrouted and unlisted, while api-key accounts are unaffected ([External Vendor Accounts §7](cross-cutting/external-vendor-accounts.md#7-feature-flag-and-routing-mode)). |
| **Model discovery (vendor account)** | Asking the vendor which models an account's own credential can use and replacing the account's static seed with the answer: at a subscription connect, at the creation of a preset account (OpenAI-compatible or native Gemini) with its key, and on an explicit "refresh models" by the account's owner or, for a shared api-key account, a co-manager. Fail-soft (a failed or empty discovery keeps the existing models). See [External Vendor Accounts §6](cross-cutting/external-vendor-accounts.md#6-dynamic-model-discovery-and-the-model-prefix). |
| **Model prefix (vendor account)** | An optional per-account namespace for the account's model ids: a model is listed and requested as the prefix plus the vendor's id (`gateway_model`), and the vendor is sent the bare id (`upstream_model`). |
| **Vendor access (API token)** | An API token's strict opt-in policy for which of the vendor accounts its principal can reach it may use (for a user token, writable at any time; for a service token, on create only): an **all** switch (every active account the principal **owns**, future ones too, under each account's own prefix, but **never a shared one**) or an explicit list, each entry with an optional **prefix override** (enabled with an empty value = the account's models under their original names, no prefix). A shared account is used only when an entry names it, so borrowing another owner's credential is always a deliberate, named choice. The default, and the state of every token at upgrade, is no vendor access. It binds API tokens only; the owner's interactive portal session sees all of their **own** accounts, never a shared one. Enforced in both the model listing and routing through `routing.TokenVendorPrefix`. See [External Vendor Accounts §11](cross-cutting/external-vendor-accounts.md#11-per-token-vendor-access) and [ADR-050](09-architecture-decisions.md#adr-050--vendor-account-access-is-a-per-token-opt-in-enforced-in-listing-and-routing-through-one-prefix-helper). |
| **Agent token** | A per-server bearer token authenticating the Server-Agent's telemetry/cert calls. |
| **API token** | A user-created bearer token for calling the inference APIs. |
| **Session + CSRF** | Browser auth: a server-side session cookie plus the `X-OP-CSRF` header on state-changing requests. |
| **Run-as token** | The `X-OP-Run-As-Token` used by the portal chat to act under a chosen API token. |
| **Principal / scope** | The authenticated identity and its scopes (`admin`, `system`); roles are `user < admin < system_admin`. |
| **Admin group** | A group with delegated management rights over a subset (servers/services/resource groups/members). |
| **Step-up (system-admin mode)** | A time-boxed elevation required for sensitive system-admin actions. |
| **Service account** | A non-human principal with delegates and an allowed-model list. |
| **Project / user group / resource group** | Scoping and organization constructs for members, quotas, and provisioning. |
| **Principal limits** | Per-principal usage/quota limits. |
| **Usage event** | A per-request record (the billable measure, cost, energy, status, attribution) used for analytics. The measure is either the five token counts or the `(billing_unit, billing_quantity)` pair — never both, and never neither. |
| **Billable measure** | What a request is counted in, recorded as a **(unit, quantity) pair** on the usage event (`billing_unit`, `billing_quantity`), never as a bare number. `billing_unit = ''` is a positive assertion that the row is **token-metered**, so the five token counts are the measure; `image` and `audio_second` mean `billing_quantity` is the measure and every token-denominated column is `0`. The two are an XOR, enforced. A scalar would mean something different on every row, so no aggregate over it could have a dimension ([ADR-041](09-architecture-decisions.md#adr-041--a-billable-measure-is-a-unit-quantity-pair-never-a-scalar)). |
| **Unpriceable** | A fourth `energy_source` value, and the only one that is not a tier: no tier could price the row, because its measure is not tokens (so Tier 3's Wh-per-token formula does not apply) and the host offered neither power telemetry nor a configured wattage. Terminal by design — the stamp is what removes the row from the reconciler's `energy_source = ''` queue, which oldest-first selection would otherwise let it block. The operator remedy is that server's `estimated_watts` ([ADR-041](09-architecture-decisions.md#adr-041--a-billable-measure-is-a-unit-quantity-pair-never-a-scalar)). |
| **Payload capture** | The opt-in, encrypted-or-volatile, redacted storage of request/response payloads. |
| **Chat blob** | One binary payload (an image today) of a portal chat, stored in its own owner-scoped `chat_blobs` row sealed with the capture key, outside the sealed transcript, and referenced from the transcript by `image_url.url = /api/portal/chat-blobs/{id}`. Served only to the chat's owner, with allow-listed types and hardened headers; resolved back to a `data:` URL for a run's upstream history ([ADR-056](09-architecture-decisions.md#adr-056--chat-binary-payloads-live-in-an-owner-scoped-sealed-chat_blobs-store-and-the-transcript-references-them-by-gateway-url)). |
| **Telemetry** | Host/GPU/power/temperature/hardware data pushed by the Server-Agent. |
| **Managed runtime** | The agent-managed model runtime: model server *processes* started and stopped on demand by the Server-Agent from launch specifications held in the gateway. Replaces llama-swap. See [Agent-Managed Model Runtime](cross-cutting/agent-runtime-manager.md). |
| **Launch spec** | The full command for one managed model — binary, argv, environment, working directory, listen port, health path, timeouts — stored per model mapping and edited in the portal. |
| **Router port** | The single HTTP port an agent exposes for all its managed models; it reads the `model` field out of each request body and reverse-proxies to the matching child process (which binds loopback only). |
| **Admission** | The agent-side decision, taken before any model process starts, that the new process may run alongside those already running: the co-residency matrix, the process limit, and the per-GPU VRAM budgets, all three. |
| **Co-residency matrix** | The operator's pairwise statement of which two managed models may run at the same time. Row present means pair allowed; it expresses *intent* and covers non-VRAM constraints, while the VRAM arithmetic is the veto. |
| **VRAM budget** | A per-`(server, GPU index)` megabyte ceiling that admission sums declared and measured demand against. An *absent* row and a row of `0` both mean unconstrained — "no budget for this GPU" is expressible either way, and admission skips the GPU identically. |
| **Feature flag (agent capability)** | A named capability, e.g. `runtime_manager`, that gateway and agent each declare; a feature is active only where both lists intersect. Versions are never compared ([ADR-025](09-architecture-decisions.md#adr-025--agent-capabilities-negotiate-by-named-feature-flags-not-versions)). |
| **Admin state** | The persisted desired-state override on a managed model: `''` (none), `force_running`, or `force_stopped`. There is no restart command — a restart is a sequence over these states. |
| **File mode** | An agent whose managed-runtime configuration comes from a local file instead of the gateway. It reports its effective configuration upward with environment values masked, and the portal becomes read-only for that server. |
| **Dialect seam** | The abstraction that keeps SQLite and PostgreSQL on one query set (`internal/store/dialect.go`). |
| **Migration** | A forward-only, versioned schema change applied transactionally on startup. |
| **Store driver** | One of `memory`, `sqlite`, `postgres`. |
| **Edge TLS** | TLS on the public listener (public ACME). |
| **Mesh TLS** | mTLS on the agent/mesh listener, issued by the internal CA. |
| **Internal CA** | The gateway-managed certificate authority for the mesh. |
| **`cert_mode=proxy`** | Agent mode that runs a TLS-terminating reverse proxy in front of the local AI server. |
| **HTTPS auto-switch** | Reconciled switching of an application's scheme to `https` (modes manual/auto/selected + per-server override). |
| **NetBird mesh** | The private WireGuard mesh linking the gateway and AI servers; peers/policies are gateway-managed. |
| **Built-in theme** | A theme compiled into the frontend bundle (may contain code). |
| **External (data) theme** | A data-only theme loaded at runtime from the themes directory; not part of the source tree. |
| **CSS-variable bridge** | The mechanism by which `ThemeRoot` writes theme tokens as CSS custom properties consumed app-wide. |
| **Dispatch** | Forwarding a resolved inference request to `scheme://domain:port` as the application's provider type. |
| **SSE** | Server-Sent Events, used for streaming inference and live portal updates (telemetry, logs, benchmarks). |
| **Reconciler** | A periodic background loop (certs, NetBird token, energy, availability) that keeps state consistent. |
| **SPDX header** | The per-file license identifier (`AGPL-3.0-only`) plus copyright line. |
