## 1. Worker `vllm-srun serve`
Install (src/model-runtime/README.md, pyproject.toml @SHA):
- Package name `vllm-srun` version 0.2.0, `requires-python >=3.10`, Apache-2.0, Linux classifier. Entry point `[project.scripts] vllm-srun = "vllm_srun.cli:main"`; also `python -m vllm_srun` (vllm_srun/__main__.py). Install from a repo checkout: `pip install torch --index-url https://download.pytorch.org/whl/cpu; pip install ./src/model-runtime` (or `make model-runtime-install`). Deps: torch>=2.4, numpy, safetensors, tokenizers, huggingface_hub, starlette, uvicorn, uvloop, httptools, prometheus_client, pyyaml. Extras: onnx, multimodal (pillow, opencv), reference, test. Otherwise it ships inside the router images (ghcr.io/vllm-project/semantic-router/vllm-sr-{cpu?,rocm,cuda}).
- Network: yes by default - downloads from the HF Hub (huggingface_hub), tokens from HF_TOKEN / token file only. `--offline` (or HF_HUB_OFFLINE=1) uses cache only; a local package directory works as MODEL (troubleshooting.md "No network").

CLI (src/model-runtime/vllm_srun/cli.py + config.py @SHA; code defaults, which differ from docs in two places, flagged):
- Subcommands: serve, models, plugins, devices, fixture.
- `MODEL ...` positional (nargs=*): HF repo id, built-in name, or local package dir; `MODEL@REVISION` pins; several models share one process. `--models FILE` (YAML) alternative (not both). `--revision` = 40-hex commit, required for a non-built-in Hub model (one MODEL only).
- `--device` default `auto` (auto | cpu | cuda[:N] | rocm[:N] | xpu[:N] | npu[:N] | mps)
- `--host` default `127.0.0.1`; `--port` default `8100` (config.py DEFAULT_PORT=8100); `--uds PATH` Unix socket instead of TCP.
- `--engine` default `auto` (native|onnxruntime) - NOTE: this is the engine *plugin*, unrelated to Engine mode of `vllm-sr`.
- `--family`, `--served-model-name` (one MODEL only; default = package name; this is the ID in /v1/models and request `model`), `--threads`, `--memory-budget GIB`, `--cache-dir`, `--offline`, `--base-path`, `--accept-licence`, `--log-level` (info), `--autotune-cache`.
- `--max-queue` 256 (queued requests per model before 429), `--max-queued-tokens` 4194304 (1<<22).
- `--max-num-seqs` / `--max-num-batched-tokens`: code default None = chosen per device class + GPU calibration (CPU constants DEFAULT_MAX_NUM_SEQS/…). DOC MISMATCH: website/docs/model-runtime/reference/commands.md lists 8192 / 65536; cli.py help text says per-device/calibrated. Trust code.
- `--batch-window-ms` 2.0 (docs), `--dtype` auto|float32|bfloat16|float16, `--enable-shared-context/--no-...`, `--max-model-len` (lowers package input limit; Decision models only).
- `--max-request-bytes` default 32<<20 = 33554432. `--max-bundle-tasks` 64. `--systemone-schema` {vllm-sr/5.0 (default), vllm-sr/4.0}.
- `--load-attempts` 5, `--load-retry-seconds` 5.0 (doubling to 300), `--result-cache-entries` 16384, `--media-workers`.
- `--forward-timeout-seconds` default 300.0 (0 disables watchdog). `--shutdown-grace-seconds` default 8.0.
- Removed flags error out: `--profile`, `--max-batch-tokens`.
- **No auth / API-key flag at all.** grep of cli.py/config.py/app.py/server.py finds no Authorization handling. website/docs/model-runtime/reference/metrics.md ("Security"): "`vllm-srun serve` binds its worker API to 127.0.0.1 unless you pass --host. Workers have no authentication; expose them only on a trusted network."
- **Multiple models: yes** (positional list or --models file; per-model name/device/dtype etc; `/health` then adds `models{}`; requests must name `model` when >1 served).
- GPU memory: there is NO vLLM-style gpu-memory-utilization flag. Relevant: `--memory-budget GIB` (refuse load if estimated above), `--max-num-seqs`, `--max-num-batched-tokens` (startup calibration on GPUs), `--dtype`, `--max-model-len`. OOM in a forward -> 413 request_too_large (alone) or 429 overloaded (shared) (http-api.md).

## 2. Endpoints (vllm_srun/api/app.py routes @SHA)
Routes: POST /v1/decisions, /v1/systemone, /v1/systemone/batch, /v1/classify, /v1/embeddings, /v1/rerank, /v1/bundle; GET /v1/models, /health, /health/live, /metrics, /openapi.yaml. **There is NO `GET /v1/systemone/models` on the worker** - that path exists only on the router/Engine listener (pkg/systemone/public.go). Worker equivalent is `models[]` inside `GET /v1/models`.

GET /health (app.py `health`, openapi `Health`): body `{"api_version":"5.0.0","status":<starting|loading|warming|ready|degraded|failed>,"reason":<str|null>,"model":<served id | null if several>}` (+ `"models":{id:{status,reason}}` when >1 model). HTTP 200 iff state=="ready", else **503**. Golden check: runtime.py sets "warming/running the golden check", golden failure -> VerificationError -> `failed`; `unverified` golden (e.g. NVIDIA GPU, no reference) still goes ready/200. A model whose forward exceeds --forward-timeout-seconds becomes `degraded` (503) until it returns.
GET /health/live: 200 `{"api_version","status":"alive"}`; 503 `{"api_version","status":"stalled","reason":"<per-model>"}` when a forward is stalled; alive regardless of model readiness.
GET /metrics: Prometheus text (`text/plain; version=0.0.4`). prometheus_client appends `_total` to Counters. Names/HELP (vllm_srun/supervision/metrics.py):
- Gauges: `vllm_srun_queue_depth` "Jobs waiting for the model worker." ; `vllm_srun_ready` "1 when the model passed its golden check." ; `vllm_srun_live` "0 while a forward has run longer than --forward-timeout-seconds." ; `vllm_srun_model_memory_bytes{model}` "Bytes of a model's loaded weights, packed layouts and reduced-precision copies." ; `vllm_srun_model_info{model,revision,family,engine,accelerator,device,dtype,numerics}` "The served model (value 1)."
- Counters: vllm_srun_requests_total{endpoint,status}, vllm_srun_questions_total{type,outcome}, vllm_srun_input_tokens_total, vllm_srun_deadline_dropped_questions_total, vllm_srun_result_cache_total{model,outcome}, vllm_srun_stalled_forwards_total{model}.
- Histograms: request_duration_seconds{endpoint}, queue_duration_seconds, forward_duration_seconds, batch_rows, batch_tokens, bundle_tasks.
- **There is NO in-flight/active-requests gauge in the worker.** Only "queued/waiting" = `vllm_srun_queue_depth` (summed over models' scheduler depth, set at scrape). In-flight exists only on the router frontend (port 9190): `vsr_model_runtime_replica_inflight{deployment,replica}` ("Locally admitted exchanges awaiting complete responses"), `..._replica_admitted_bytes` (reference/metrics.md).
GET /v1/models: `{"object":"list","api_version":"5.0.0","data":[ModelCard...],"limits":{"max_bundle_tasks":64,"max_request_bytes":33554432},"models":[{name,description,release_date,(5.0: version:"5.0",features:[question types],card:{...})}]}` (decision models only in `models`). ModelCard (openapi.yaml): required id, object, family, surfaces, ready; also owned_by, repo, revision, model_sha256, manifest_sha256, question_types[], presets, modalities (text|image|video), image_placements, usage, heads, embedding, rerank, **limits** (ModelLimits: `max_input_tokens`, `validated_input_tokens`, `max_request_tokens` (state-once), `max_scan_tokens`, `truncate_tokens`, min/max_options, min/max_levels, max_inputs, image_*/video_* limits), licence, engine_args{max_num_seqs,max_num_batched_tokens,batch_window_ms,dtype,enable_shared_context,max_model_len}, numerics, engine, accelerator, accelerator_validated, device, dtype, parameters, ready, status, reason, golden{status:pending|matched|unverified|failed,checked,matched,reference}, plugins. `limits.max_input_tokens` is in the card at `data[].limits.max_input_tokens` - confirmed, is the operator-lowered value when --max-model-len is set (engine-args.md#input-limit). Fields in `limits` are per-family, so max_input_tokens may be absent (e.g. non-decision heads, state-once uses max_request_tokens too).
POST /v1/systemone, /v1/systemone/batch, /v1/decisions: request = {model?, state, questions{id:{type: choice|noul|score|(box|set|span),instructions,criteria...}}, roles?, assets?, options{deadline_ms,return_meta,max_tokens,long_context}}; batch = {model, requests{name:{...}}, options} -> {model,responses,usage}. Content-Encoding gzip/zstd, multipart/form-data accepted; header `TypeSafe-Danger-Zone-Long-Context`. Response Server-Timing header. /v1/decisions answers a failed question inside a 200; /v1/systemone fails the whole request.
POST /v1/classify, /v1/embeddings (OpenAI-compatible), /v1/rerank, /v1/bundle: see openapi.yaml paths (classify/embeddings/rerank only for models whose surfaces include them; decision models answer 422 unsupported_surface).

## 4. Engine mode (`vllm-sr serve <model> --engine`) (src/vllm-sr/INSTANCE_MODES.md, website/docs/model-runtime/reference/commands.md, website/docs/api/router.md, pkg/systemone/public.go @SHA)
- Needs Docker or Podman for the default docker target (`--container-runtime docker|podman`; quickstart "You need ... Docker or Podman, Python 3.10+, 12 GiB memory, ~9 GB disk"); images vllm-sr (cpu), -rocm, -cuda via `--platform`; Kubernetes target also exists. The worker runs *inside* the router container behind a private Unix socket (VLLM_SRUN_DIR, mode 0700); `vllm-srun` is not run on the host.
- Public listener: port **8899** (standalone Router frontend, "standard local stack"); management API 127.0.0.1:**8080** (`/health`, `/ready`, `/startup-status`, `/api/v1/inventory/model-runtime`); metrics 9190. Health/readiness is on the MANAGEMENT port, not the 8899 listener (router.md "Check health or readiness: Management API on 8080"; docs also name `/health` and `/ready` as part of the System One stability promise).
- Discovery: `GET /v1/systemone/models` -> `{"object":"list","data":[{"id","object":"model","api":"systemone","routing":false,"question_types":[...],"modalities":[...]}]}`; `GET /v1/models` on the listener also works and adds `models:[{name,description,release_date}]` (public.go). **The listener's model list carries NO `limits`/`max_input_tokens`** (publishedModels() emits only id/object/api/routing/question_types/modalities). Models must be explicitly granted via `listeners[].apis.systemone.models` (INSTANCE_MODES.md says `listeners[].systemone.models` - doc inconsistency), else 404 `systemone_not_published`.
- Auth: listener `api_keys`; none set => open. Accepted headers: `Authorization: Bearer <key>` (case-insensitive "Bearer") OR `Api-Key: <key>`; else 401 `invalid_api_key` with `WWW-Authenticate: Bearer realm="vllm-semantic-router"`. Applies to POST and the GET listings.
- Endpoints on listener: POST /v1/systemone, POST /v1/decisions (alias), GET /v1/systemone/models. Worker-only APIs (classify, embeddings, rerank, bundle, /v1/systemone/batch via worker) are NOT published by the listener ("The frontend never publishes it").
- Router-side errors differ from the worker's: 504 `systemone_deadline_exceeded` after a 30 s default budget (options.deadline_ms overrides; listener `apis.systemone.max_deadline_ms` default 10 min); 429 `overloaded` + Retry-After 1, 503 `not_ready` + Retry-After 5 (http-api.md).
- Attaching a worker you run: deployment `endpoint:` in canonical YAML; `auth: {api_key_env|api_key_file}` is how the router sends a key to a remote System One API (remote-services.md) - the vllm-srun worker itself does not check one.

## 5. Error envelopes / 501
- Worker request-level errors (errors.py REQUEST_ERROR_STATUS): `{"error":{"code","message","reason?","question?","state?","question_error?","limit?"}}`: invalid_request 400, model_not_found 404, request_too_large 413, unsupported_media_type 415, unsupported_surface 422, overloaded 429, internal_error 500, not_ready 503, question_failed (System One whole-request failure).
- Per-question codes (ItemError): invalid_question 422, invalid_input/max_length_exceeded/scan_budget_exceeded 400, invalid_model_output 500, unavailable 503, deadline_exceeded 504 (SYSTEMONE_QUESTION_STATUS).
- **No 501 anywhere** (grep of errors.py, openapi.yaml). An unsupported question type (e.g. `span` on d3, `box` on non-turbo) is `invalid_question` with `reason` `type_unsupported` / `box_unsupported` / `track_unsupported`: inside a 200 answer on /v1/decisions; on /v1/systemone the whole request fails 422 `question_failed`. Decision models called on /v1/classify etc. -> 422 `unsupported_surface`.
- Envelope depends on schema and path (api/schemas.py `error()`): on /v1/decisions or under `--systemone-schema vllm-sr/4.0`: `{"error":{...},"detail":<message>,<flat code/question/state/reason/limit>}`. On /v1/systemone and /v1/systemone/batch under default vllm-sr/5.0: **`{"detail": <string>|[{"loc":["body","questions",id],"msg","type"}] (list on 422), "code","question","state","reason","limit"}` with NO `error` key**, and `overloaded` becomes HTTP **529** (not 429) with `Retry-After: 1`; not_ready 503 with `Retry-After: 5`. A gateway must parse both shapes.

## 6. d3 checkpoints / loading
Built-in d3 (website/docs/model-runtime/supported-models/decision-3/overview.md; `vllm-srun models` lists pinned revisions): vllm-sr/d3-edge (0.595B, 4 GiB), d3-lite (0.853B, 4), d3-nano (2.21B, 8), d3-mini (4.54B, 16; pinned a475367de0d8), d3-flash (8.39B, 32), d3 (26.1B, 72), d3-turbo and d3-ultra (26.1B state-once, box/track). Quantized: vllm-sr/d3-FP8, d3-W4A16-AWQ, d3-W4A16-GPTQ, d3-NVFP4, d3-NVFP4-AWQ. All answer choice/noul/score (+set as noul-per-label); **no span** (bind pii/hallucination elsewhere, e.g. vela3-fast; Vela 3.0 vela3-fast is the router's default CPU decision model). d3 runs BF16 on GPU, FP32 on CPU; "The family runs on a GPU" (overview) although CPU is supported; ROCm image PyTorch lacks CPU LAPACK; golden references recorded for CPU/NPU/ROCm, none for NVIDIA (-> `unverified`, still ready).
Loading: resolved from HF Hub by repo id (pinned built-in revision, files verified by SHA-256 / MODEL_MANIFEST.json, no trust_remote_code); or local package directory; cache = HF_HUB_CACHE / `--cache-dir` (router images: VLLM_SRUN_CACHE_DIR=/app/models/model-runtime).
Cold start: no number documented. Docs: "first start downloads the model... Large models take minutes"; router wait bounded by VLLM_SRUN_READY_TIMEOUT default 10m; states loading -> warming (golden check, GPU calibration) -> ready. Weights d3-mini ~9.1 GB BF16 / 18.2 GB FP32.

## 7. Supervision
- Signals: uvicorn handles SIGTERM/SIGINT; `timeout_graceful_shutdown=--shutdown-grace-seconds` (8 s); then `runtime.stop`; if a forward still runs the process `os._exit(4)` (server.py ABANDONED_EXIT=4); a device error exits with 3 after 0.5 s (runtime.py `os._exit(3)`). UDS socket file removed on exit. K8s example (kubernetes.md): readinessProbe GET /health, livenessProbe GET /health/live, command `vllm-srun serve vllm-sr/d3-edge --device rocm:0 --host 0.0.0.0 --port 8100`.
- The router's own supervision: restarts an exited worker with 1 s..60 s back-off, stops via SIGTERM then SIGKILL after 10 s (configuration.md).
- Readiness: /health 503 until ready; the load itself is in a background thread (`runtime.start(background=True)`), HTTP is up immediately, so /health/live=200 and /health=503 during load. Failed loads retry `--load-attempts` (5) with doubling delay; golden/package failures are never retried and stay `failed`.

## Contradictions with our assumptions
1. "Worker on loopback without auth": CONFIRMED (default 127.0.0.1:8100, no auth at all). Engine mode listener (8899) is the authenticated one (Bearer or Api-Key), but only if `api_keys` configured.
2. "Readiness /health 503 until golden answers pass": CONFIRMED, but 503 also covers `degraded` (stalled forward) and `failed`; `unverified` golden is still 200. Body status vocabulary is starting|loading|warming|ready|degraded|failed.
3. "Liveness /health/live (stalled)": CONFIRMED (200 alive / 503 stalled). Stall only after --forward-timeout-seconds (300 s default).
4. "Context limit at /v1/models data[].limits.max_input_tokens": CONFIRMED on the worker, with caveats: field set is family-specific (state-once models add max_request_tokens; validated_input_tokens is the default cap unless `options.long_context`), and the Engine listener's /v1/models and /v1/systemone/models do NOT expose limits.
5. "Detection by binary name vllm-srun / vllm_srun": binary `vllm-srun` and module `vllm_srun` are right, BUT it is not pip-installable from PyPI (checkout/image only), so detection cannot rely on a pip install; Engine mode spawns it only inside the container.
6. No in-flight gauge on the worker (only vllm_srun_queue_depth).
7. No 501; errors are 422 invalid_question/unsupported_surface; and 5.0 /v1/systemone errors use `detail` + flat fields and 529 for overload.
8. api_version majors changed 3->4->5 within days (Nov 9-11 2026); the router hard-refuses another major; pin a commit/image.
9. /v1/systemone/models does not exist on the worker (only router/Engine listener).
10. Docs vs code: commands.md says --max-num-seqs 8192 / --max-num-batched-tokens 65536; code defaults are device-chosen (None). INSTANCE_MODES.md vs quickstart disagree on `listeners[].systemone.models` vs `listeners[].apis.systemone.models`.
